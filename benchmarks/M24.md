# M24 selective-read layout feasibility

Status: in progress. The initial probe rejects the original
one-block-per-range-GET, ID-sorted physical layout for the declared quality
and cold-request envelope. Later sections measure the vector-local seal and
an opt-in selective reader; none accepts M22–M24.

## Eight-block oracle bound

The [raw result](m24/layout-id-sorted/run.json) loads the M21 SHA-256-verified
SIFT1M 250,000 × 128 prefix into the experimental segmented namespace with
100-row writes, a seal every 64 writes, and run consolidation. The selected
root has 12 runs and 1,292 addressable blocks. For each of the first 200 query
vectors, an independent f64 squared-Euclidean scan finds exact top-10 IDs,
both unfiltered and with the 1% `id % 100 == 0` cohort. The first result in
each class is checked against `SegmentedDatabase::search_exact`. For each
query, the probe chooses the *best possible* eight of the actual committed
blocks, using knowledge of the exact answer, and counts how many top-10 IDs
those blocks contain. No routing algorithm can exceed this coverage while
reading at most eight individual blocks from this root. The selected reader
currently issues one range GET per uncached block, so eight blocks correspond
to its <=8 cold query-GET ceiling before metadata requests. The bound ignores
routing cost, index bytes, cache misses and latency; actual ANN recall can only
be lower for this read pattern.

| 200 queries, k=10 | Optimistic mean recall | 5th percentile | Queries below 0.90 | Mean target |
|---|---:|---:|---:|---:|
| Unfiltered | 0.855 | 0.80 | 118 | >=0.90 |
| 1% equality filter | 0.800 | 0.80 | 200 | >=0.90 |

Unfiltered exact neighbors occupy ten distinct blocks in 118/200 queries and
nine in another 54. Filtered exact neighbors occupy ten distinct blocks in all
200 queries. A different range grouping, smaller blocks or a new vector-aware
derived layout needs its own byte/GET analysis; this experiment alone is not a
proof against every possible layout of these records. It does show that adding
candidate routing to the current one-block-per-GET reader cannot meet the
declared mean recall with eight cold block fetches.

Reproduce with
`python3 tools/m24_layout_probe.py NEW_OUTPUT --data DATA_DIRECTORY`, where
the directory contains the verified M21 base prefix and query file. The
runner records input/source hashes, Rust version and hardware. This is a local
file-backed layout/oracle experiment, with the complete input vectors held in
the offline oracle process. Its load and oracle times are not serving latency,
RAM compliance, S3 traffic or cost evidence. The result supplies a layout
decision only. M22–M24 still need a generation-bound selective reader,
independent MinIO read/write traffic, exact-oracle ANN quality, bounded
resources, cache-loss behavior and the declared cost gates.

## Vector-local layout and routing feasibility

The [second raw result](m24/layout-vector-bisect-quantized/run.json) reuses
the same hashed corpus and exact IDs. A deterministic balanced recursive
two-center split groups records by vector into 1,471 blocks of 169–170 rows.
The 1% equality cohort is grouped separately into 15 blocks of 166–167 rows;
this is a filter-specific derived copy, not a general predicate solution.
The split refines each balanced cut three times. The experiment chooses eight
blocks and counts exact top-10 IDs within them, which is the recall exact
reranking could attain after fetching those blocks.

| Eight-block selection | Unfiltered mean / 5th percentile | 1% filtered mean / 5th percentile |
|---|---:|---:|
| Oracle best blocks | 0.981 / 0.90 | 1.000 / 1.00 |
| Nearest block centroids | 0.650 / 0.10 | 1.000 / 1.00 |
| Nearest of 16 representatives per block | 0.484 / 0.10 | 1.000 / 1.00 |
| 4-bit per-component sketch, scan all codes, rank blocks by minimum approximate distance | 0.945 / 0.80 | 1.000 / 1.00 |
| 8-bit sketch, same routing | 0.980 / 0.90 | 1.000 / 1.00 |

The 4-bit sketch has 16,000,000 packed code bytes for the full collection and
160,000 for the filter-specific copy, excluding block mappings and allocator
overhead. Each component uses a dataset-min/max affine codebook. The offline
probe reconstructs codes into an unpacked float matrix for routing; it does
not demonstrate that a serving implementation fits the 64 MiB whole-engine
RSS or 50 ms warm-query budgets. The 4-bit result meets the declared *static*
quality mean and fifth-percentile thresholds only when all rows are regrouped
globally; it does not cover updates,
deletes, index visibility or short-result behavior under load. The first
eight-block oracle result establishes that a vector-local layout can put the
answers in eight blocks, while the centroid/representative failures show that
small block summaries alone did not route these queries adequately.

A separate approximation groups consecutive 6,400-row increments independently,
matching the M22 seal cadence but not its actual consolidated-run boundaries.
It yields 1,485 blocks and a best-eight-block ceiling of 0.946 mean / 0.80
fifth-percentile recall. The 4-bit route drops to 0.895 / 0.70 and fails both
quality thresholds; 5-bit reaches 0.925 / 0.80 using 20,000,000 packed full-corpus
code bytes, and 8-bit reaches 0.944 / 0.80 using 32,000,000. These are static
logical results, not a sustainable update plan. In particular, rebuilding the
global layout every seal would rewrite the full base and contradict M21's
upload gate. Incremental publication needs its own encoded-byte, overlap,
visibility, quality and failure measurements.

Reproduce with NumPy 2.3.5 and
`OPENBLAS_NUM_THREADS=1 python3 tools/m24_vector_layout_probe.py NEW_OUTPUT --data DATA_DIRECTORY`.
The raw result records the input, prior oracle and script hashes. The groups
are logical; no block bytes were encoded or fetched. Thus <=128 KiB/block,
<=1 MiB/query, <=8 GET, actual reranking time, durability and cost remain
unverified. A bounded, generation-bound derived vector-local layout plus a
compact routing sketch remains a candidate. It must first prove encoded block
sizes, update maintenance and memory/latency budgets on MinIO. No milestone
acceptance follows from this offline result.

## Encoded vector-local seal

The experimental seal now groups put records through balanced vector cuts,
then sorts IDs within each block and splits any block over 128 KiB. Deletes
remain separate. The fixed-width run index stays ID-sorted and points to
arbitrarily ordered immutable blocks. Log acknowledgement, pack/index/root
publication and selected-root recovery retain their existing versioned
contract. Reordering the one authoritative sealed copy avoids paying for a
second full-vector upload on every write; the ID index still resolves point
reads. This choice leaves sparse-filter routing unsolved rather than assuming
that the same grouping serves every predicate. The
[actual-root local probe](m24/layout-vector-local-seal/run.json)
uses the same verified 250,000-row load and 200-query independent exact oracle
as the ID-sorted probe. It found 12 runs and 1,485 blocks. Perfect selection
of eight actual blocks reaches 0.9455 mean / 0.80 fifth-percentile recall
unfiltered, but only 0.841 / 0.80 for the 1% filter. The mean/max sum of the
eight selected encoded payloads is 821,173/913,347 bytes unfiltered and
896,306/911,386 filtered; none of the 200 sums exceeds 1 MiB. This is an
optimistic payload-only result, not measured HTTP transfer or GET count.

An offline five-bit scan of all 250,000 codes, selecting eight blocks by the
minimum approximate distance and then counting exact-neighbor membership,
reaches 0.925 mean / 0.80 fifth-percentile recall unfiltered. Its logical
packed code size is 20,000,000 bytes. The probe held unpacked codes and the
input corpus in RAM and spent 2,591 ms routing 200 queries; that time excludes
block reads and exact reranking and is not a serving-latency result. The
filtered eight-block ceiling fails the 0.90 mean target, so a separate
filter-aware path is still required.

The [MinIO load/recovery probe](m24/vector-local-minio-250k/run.json) uses the
same 100-row writes, seal every 64 logs and run consolidation as the earlier
M22 250k baseline. It uploaded 371,263,692 bytes in 2,834 PUTs versus
369,528,272 bytes in 2,833 PUTs for the prior ID-sorted probe. Its unpaced
load took 16.247 s, peak whole-process RSS was 55,164,928 bytes, the longest
seal planner call was 59.278 ms and the longest seal step 56.677 ms. Reopen
took 70.896 ms with 17 GET and one LIST, and a full exact scan matched the
independent oracle with 1,485 GET. That exact scan remains far outside query
gates. The targeted `python3 tools/test_s3.py --segmented-only` MinIO fault
suite passed after adapting mixed-pack reclamation to overwrite three of each
four IDs; it exercises lost responses after log, pack, index and root writes,
reopen, cache loss and corruption, and fail-closed selected-pack reads.
The disposable container was removed after each run. These unpaced checks do
not establish independent traffic, p95 latency, update-wave quality or cost
acceptance. M22–M24 remain in progress.

## Packed-sketch selective-read prototype

The [MinIO selective run](m24/selective-prototype-minio-250k/run.json) loads
the same verified 250,000 × 128 corpus into the vector-local root, then opens
a new database process and builds an opt-in in-memory five-bit sketch from
authenticated blocks. The sketch charges 23,144,032 bytes against a 24 MiB
index budget; it stores packed codes, IDs, block ordinals and a per-dimension
affine codebook. Building makes two full root passes. The query scores all
codes, selects eight blocks, reads them through the M23 RAM/NVMe cache,
discards shadowed records and exactly reranks surviving vectors plus the
acknowledged tail. It supports **unfiltered** queries only. Root publication
invalidates the sketch; no derived object is yet stored in S3.

The first 200 SIFT1M queries were checked against the independent exact IDs
from the actual-root probe. The process used 4 MiB RAM and 256 MiB NVMe block
cache budgets. “Cold” means empty engine cache after sketch build, not flushed
host/MinIO caches. The second pass repeats those queries with warmed NVMe.

| Local MinIO, 250k × 128 | Observed | M21 target |
|---|---:|---:|
| Unfiltered mean / 5th-percentile recall@10 | 0.9255 / 0.80 | >=0.90 / >=0.80 |
| Short results | 0 / 200 | <1% |
| First empty-cache query | 58.687 ms, 8 GET, 903,563 block bytes | <=200 ms, <=8 GET, <=1 MiB |
| Warm second-pass query p95 | 31.515 ms, 0 GET | <=50 ms, <=2 GET |
| Peak whole-process RSS | 63,979,520 B | <=64 MiB |
| Charged NVMe occupancy | 109,146,112 B | <=256 MiB |
| Fresh-process root open | 120.398 ms, 14 GET | <=1 s, but sketch absent |
| Sketch build after open | **7,337.992 ms, 2,970 GET** | Ready within <=1 s |

The first pass contains cold misses and cache warming; its p95 was 55.434 ms
and is not the NVMe-warm class. Across that pass the maximum query used eight
GET and 913,347 authenticated block bytes. The second pass used zero remote
GET and bytes for all 200 queries. Deleting the entire cache directory,
reopening and rebuilding from S3 preserved the first query's IDs; rebuilding
took 6,987.680 ms and the query refetched 8 blocks. MinIO fault/recovery
tests still pass, and each disposable container was removed.

This is a measured selective query path, but **M24 is not accepted**. Effective
fresh-process readiness exceeds one second, root changes invalidate the
in-memory sketch, the 1% filter is unsupported by this path, and no
independent read/write load or complete storage-work/cost acceptance has run.
The prototype demonstrates that a bounded packed router and cache can meet
static unfiltered quality, query-byte, warm-latency and RSS budgets. A
generation-bound persisted derived sketch with incremental update visibility
is required before the same behavior can serve the declared workload without
full rescans. S3 remains authoritative; loss of the disposable cache changes
latency, not the answer.

## Sketch codebook granularity decision probe

The [local 250k-row comparison](m24/sketch-granularity-local-250k/run.json)
repeats the same deterministic seal, 200 SIFT1M queries and independent exact
oracle. Each five-bit route scores every vector, selects eight committed blocks
and counts exact top-ten IDs in those blocks. The run-local variant fits a
separate affine codebook to the current physical blocks of each run; the
block-local variant fits one per block. This is an **offline optimistic routing
probe** with unpacked resident codes, not a measured serving path.

| Codebook scope | Groups | Mean / fifth-percentile recall@10 | Codebook bytes |
|---|---:|---:|---:|
| Whole root | 1 | 0.925 / 0.80 | 2,048 |
| Run | 12 | 0.9295 / 0.80 | 24,576 |
| Block | 1,485 | 0.936 / 0.80 | 3,041,280 |

All three use 20,000,000 packed code bytes before IDs, ordinals and allocation
overhead. The block-local books improve mean coverage by 0.0065 over run-local
but would add about 3 MiB to the already 23.14 MB charged prototype sketch,
breaching its 24 MiB index budget without reducing other state. Run-local
books meet the static unfiltered quality gate with small additional state and
can be formed when a bounded seal group is available. This favors immutable
seal-group sketch components that survive index consolidation. It does not yet
show their persisted format, update cost, root binding, fresh-process latency,
or filtered quality; those remain acceptance work.

## Single-machine acceptance protocol (declared before the run)

`python3 tools/m24_acceptance.py NEW_OUTPUT --data DATA_DIRECTORY` runs the
M21 envelope unchanged on disposable loopback MinIO in three processes:

1. `load` writes the hashed 250,000 × 128 SIFT1M prefix in 100-row batches
   with `cohort=one-percent` on IDs divisible by 100, into a namespace whose
   metadata declares that predicate resident. Maintenance runs inline.
2. `serve` opens a fresh process (claim, root, indexes, tail and persisted
   sketches; no rebuild), answers the first 200 SIFT1M queries twice in each
   class against the independent exact IDs of the actual-root probe (the
   first pass starts with an empty engine cache), then runs 300 seconds of
   the M21 traffic: four writers each offer one 100-row overwrite batch per
   second using the 137-position rotation, and four readers each offer one
   query per 100 ms, alternating unfiltered and filtered, from held-out query
   rows 200 onward. Each producer keeps one request outstanding, skips slots
   more than one period late and counts overloads without retry.
3. `verify` reopens in a fresh process, scans every authenticated live
   document once, compares each value with its expected generation, computes
   an exact oracle for 100 unfiltered and 100 filtered held-out queries in
   the same scan, then checks cache loss and a backup restore.

Serving configuration: `SegmentedServingOptions::m21` (seal at 32 unsealed
logs; an unfiltered query ranks 12 blocks and, in rank order, widens one
span per pack while spans fit 8 range requests and 1 MiB; four-object cleanup
units;
24 MiB sketch budget; no RAM block tier and a 256 MiB NVMe block cache; four
query threads) and the default M16 admission bounds with read priority over
writes younger than 50 ms. This configuration was revised after the
preliminary run below and before the final run. Latency gates use client end-to-end time. An unfiltered query is
"cold" if it fetched any block from object storage and "warm" otherwise;
filtered queries read no blocks. Peak RSS is `ru_maxrss` of the serve process,
which never holds the corpus; macOS peak physical footprint is also recorded.
Visible payload is measured with `mc du` after `serve`. The cost model
multiplies measured request counts by the US East (N. Virginia) S3 Standard
list prices retrieved on 2026-09-30 from <https://aws.amazon.com/s3/pricing/>:
$0.005 per 1,000 PUT/COPY/POST/LIST, $0.0004 per 1,000 GET, free DELETE and
$0.023 per GB-month. Every M21 gate is evaluated as declared; a failure is
reported, not relaxed.

## Acceptance runs

All runs below used the declared workload on local Docker MinIO (Apple M4,
macOS 26.6.2). Each run's `run.json` records its git revision, source
digests, every measured class, the gate verdicts and the cost model.

The [preliminary run](m24/acceptance-minio-250k-preliminary/run.json) used
JSON blocks, separate sketch objects and an 8-block read. Its source digests
were taken after the run and do not identify the binary. It met every gate
except 7.1 PUT/s, 7.0 DELETE/s and 0.895 update-wave recall. Splitting
requests by object kind showed logs alone take 4 PUT/s and 4 DELETE/s, so
maintenance had about 2/s left; sketches then moved into their packs and
reclamation began merging packs.

The update-wave oracle shows the best possible choice of any eight committed
blocks reaches 0.916 while the reader reaches 0.912, so after heavy
overwrites the layout, not routing, bounds recall within eight range
requests. The 30-day cost model at the offered rate is about USD 94, almost
all PUT requests.

In v2, peak physical footprint stayed below 64 MiB, but `ru_maxrss` also
counts freed pages macOS has not yet reclaimed. Per-command attribution in
`engine_profile` pointed at reclamation, query span buffers, seal and
consolidation transients. A mimalloc global allocator was measured and
rejected (120 MB RSS, per-thread heaps). The final revision keys the block
cache index by 32-byte digests with tick-ordered LRU, shares fetched span
buffers among their blocks and stores sketch row IDs as u32 offsets.

**The final run accepts the declared single-machine envelope on local MinIO:
every M21 gate passed.** Peak RSS was 64,372,736 B (54,362,544 B footprint),
fresh open 329 ms and reopen after traffic 368 ms. Quality, latency and
storage work match v2: 0.9455 / 0.80 static and 0.912 / 0.80 update-wave
unfiltered recall, exact filtered results, warm / cold / filtered / write p95
of 36.3 / 42.1 / 9.2 / 38.9 ms, at most 8 GET and 421,508 B per cold query,
5.96 PUT/s, 5.90 DELETE/s, 1.07 MiB/s upload, no LIST, 70,690,874 B visible,
32.8 MB of NVMe cache, 0 lost writes among 250,000 checked values, and equal
results after cache loss and backup restore. The MinIO segmented fault suite
(`python3 tools/test_s3.py --segmented-only`) passed on the same revision.
Margins are narrow for PUT/DELETE rate and update-wave recall; any change to
seal, reclamation or the read budget needs a new run.

## Bounded AWS S3 check

The unresolved provider question was whether the protocol behaves correctly
on real S3 Standard: conditional create, range GETs at block offsets,
concurrent batched reads, staged publication, reopen and recovery. A full
250,000-row run from the development laptop would move more than 700 MB over
its connection, so the check used the same harness at reduced scale:
`GLIDER_M24_ROWS=25200` (63 overwrite slots per writer), 60 seconds of M21
traffic, no static oracle (it covers 250,000 rows) and no backup copy. It ran
from the development laptop on battery power, via the same home or mobile
network as the [earlier AWS diagnostics](AWS_DIAGNOSTICS.md), against bucket
`glider-pilot-test-t1g1p` in `eu-central-1` under a fresh `glider-pilot/`
prefix, which was deleted afterwards (0 objects listed).

The first attempt failed on a connection reset during load; the engine
treated the uncertain PUT as fatal, as designed. The second found a real
defect: when remote seal steps were slower than the log tail grew, a write at
the 64-object tail bound returned `MaintenanceRequired` instead of finishing
the idle seal in progress. Commit `8eeef70` fixes it with a regression test.
The [third attempt](m24/aws-25k/) completed:

| AWS, 25,200 rows, 60 s | Observed |
|---|---:|
| Load (252 batches) | 67 s, 288 PUT |
| Fresh open / reopen after traffic | 9,878 ms, 50 GET / 17,856 ms, 70 GET |
| Values checked; mismatches | 25,200; 0 |
| Update-wave unfiltered recall mean / p5; filtered | 0.999 / 1.0; 1.0 |
| Cache loss | results equal |
| Write p50 / p95 | 1,022 / 3,376 ms |
| Unfiltered warm / cold p95 | 1,362 / 3,770 ms |
| Late slots skipped (writes / queries) | 69 / 2,168 |
| HTTP or transport errors | 0 |

Correctness, conditional publication, range reads and recovery hold on S3
Standard. Latencies are dominated by the client's network round trips (about
a second per remote write from this laptop), so they say nothing about an
in-region deployment, and the M21 latency gates were not evaluated against
AWS. **A remote latency acceptance remains pending** until a client in the
bucket's region repeats this harness at full scale; that needs compute this
project has not provisioned.
