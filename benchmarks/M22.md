# M22 segment and selective-read layout

Status: range reads and an experimental segmented publication API exist behind
`experimental-segmented`. Small-index coalescing, staged mixed-pack reclamation
and pruning of fully dead blocks are measured below. Production serving, cache,
independent-load and larger-than-RAM acceptance remain pending.

## Decision tied to M23

The [M21 measurement](M21.md) found a 99.921 ms write-queue p95 at 10,000 rows
against 75 ms: four full snapshots uploaded 15,041,800 bytes while 80 changed
100-row batches uploaded 5,113,299 bytes. At 250,000 rows, routine full-base
rewrites violate the declared <=2 MiB/s upload gate by the structural
extrapolation in M21. The new layout must publish changed rows and allow a
query to fetch only selected vector blocks.

Use immutable physical segment objects targeted near 1 MiB, containing logical
blocks no larger than 128 KiB. The root manifest records each object's complete
payload length and, for each logical block, offset, length and SHA-256 of its
exact bytes. Blocks will carry a versioned record format and vector-partition
summary; each block is independently decodable and verifies before use. The
same `(immutable key, offset, length, digest)` identifies a RAM or NVMe cache
entry. Root/index metadata and in-flight block bytes count against the RAM
budget. An S3 range GET can transfer one selected block without fetching the
whole packed segment. This is a design target, not an on-disk format yet.

Small physical objects would let the current `get` validate an entire block,
but about eight times as many PUTs and keys would be needed for the same base
payload. One large indivisible object minimizes PUTs but makes each cold miss
transfer about 1 MiB. Packing keeps PUT count low while retaining a 128 KiB
read unit. Rewriting changed partition blocks was rejected in M21 because
scattered 100-row updates touch many blocks. No compression or ANN quality
benefit is assumed by this choice.

`ObjectStore::get_range` now takes key, payload offset, slice length and
expected complete payload length. S3 checks the complete envelope length and
rejects an oversized or short response. A range read does not verify the
whole-object `VTOBJ001` checksum: the caller must compare the selected bytes
against the block digest committed in a root before decoding or caching. Full
`get` still validates the complete envelope. Missing objects, length mismatch,
slice mismatch or digest mismatch must fail the dependent read; a cache miss
may refetch only within an explicit request/deadline budget. No write can be
acknowledged by cache state.

## Publication contract to implement

The new layout needs its own explicitly versioned metadata, root, block and
directory schemas. New metadata must make old readers reject this layout; an
existing namespace must be migrated through a validated fresh destination,
not reinterpreted in place. Keep one exclusive owner and one committer.
Successful immutable mutation-log publication remains the write acknowledgement
and query-visible boundary. A root covers a fixed sequence and carries retry
receipts/revision state plus references to immutable base and delta blocks.
Publish referenced blocks first, then one immutable root. Unpublished blocks
are never authoritative. A root error or uncertain response poisons writes and
maintenance; recovery chooses the highest complete valid root and replays
contiguous newer logs. Invalid selected roots or missing referenced blocks fail
closed. Deletes are tombstones and later sequence wins for an ID. Readers pin
one root and overlay newer acknowledged logs.

Reclamation follows durable root publication. A block or log cannot be deleted
while any selected root or pinned reader needs it; keys are never reused.
Bound the number of delta runs, metadata bytes, staging objects, deletion
backlog and replay tail. Spread any large merge across bounded steps fixed at
one input sequence, and reject new writes before resource bounds are exceeded
if maintenance falls behind. A faster worker alone is not a durability plan.

## Targeted infrastructure check

`python3 tools/test_s3.py --range-only` runs one disposable MinIO test. It
creates a 1,048,576-byte payload, reads a 131,072-byte interior slice with
one S3 GET, checks exact bytes, verifies missing-object and wrong-length
behavior, rejects invalid bounds before network I/O, and removes the container.
The local-store default also checks the slice and full-object length. These
tests establish the range API contract on MinIO; they do not measure query
latency, wire bytes, cache effects, block-digest enforcement by a reader, or
crash recovery of a future segment format.

The experimental namespace uses metadata v2 and root/block/index/log v1. A log
PUT acknowledges a write; the highest immutable root generation covers a fixed
acknowledged sequence, with newer contiguous logs replayed. Maintenance freezes
one sequence, creates packs and a fixed-width ID index in separate steps, then
publishes one root. Each attempt uses fresh object keys so an orphan from a
failed attempt cannot block a later plan. The root carries retry receipts and
revision state. An index entry points to an independently hashed block; a
delete remains a tombstone. A conditional conflict can advance the root without
a data run. Obsolete objects are removed only after publication in bounded
cleanup calls. Any uncertain create or delete requires reopening before another
write or maintenance step. The 64-log replay tail and 64-run limit currently
apply backpressure; long-term physical reclamation and object growth are not yet
fully bounded. The caller must enforce exclusive namespace ownership and takeover
isolation. `search_exact` scans authenticated blocks and serves as a correctness
oracle, but has no selective candidate path. No migration from old namespaces
is provided.

The experimental `consolidate_runs_step` merges one adjacent pair when the
older run's ID-index size tier is no larger than the newer run's and their
combined input indexes total at most 1 MiB. It publishes a fresh index and
then a fresh root generation, retaining only latest IDs; a tombstone in the
oldest pair can be removed with its shadowed value. It reuses immutable data
blocks and cleans their packs only when no referenced block remains. This is
bounded index maintenance; a separate step handles mixed live/stale packs.

`python3 tools/test_s3.py --segmented-only` runs the disposable MinIO recovery
check. It injects response loss after log, pack and root PUTs and an obsolete
DELETE, then reopens, verifies acknowledged retry outcomes and documents,
republishes after an orphan with a changed plan, and finishes cleanup. It also
recovers uncertain consolidation and pack-reclamation roots, and rejects a
selected root whose referenced pack was removed. A local test covers writes
arriving during fixed-boundary publication and staged reclamation. These are focused protocol
checks, not an M22 workload acceptance.

## First 250,000-row probe

The [raw local MinIO result](m22/capacity-probe-250k/run.json) loads the verified
SIFT1M prefix in 100-row batches from a streaming input, seals every 64 logs,
cleans obsolete objects, reopens, checks sample IDs, and compares one unfiltered
exact k=10 query with an independent file-streaming oracle. Apple M4/macOS
26.6.2, pinned MinIO image, Rust release build. The 15.701 s unpaced load
issued 2,777 PUT, 2,539 DELETE and uploaded 348,253,673 request-body bytes;
the maximum individual seal step was 73.395 ms. Load peak RSS was 38,879,232
bytes; process peak after reopen/query was 47,054,848 bytes. Reopen took
141.214 ms with 45 GET and one LIST. The exact result matched the oracle, but
one scan required 1,292 GET and 3,804.787 ms. These are a load/recovery probe,
not independent read/write traffic, a cache measurement, or an ANN quality
result. They demonstrate the addressable layout can be populated beyond 64 MiB
of raw vectors while the exact full scan fails the selective-query request and
latency gates. M23/M24 need a candidate path, bounded caches and request-byte
measurements; increasing a cache alone cannot turn the full scan into <=8
cold GETs.

The [same probe with run consolidation](m22/capacity-probe-250k-consolidated/run.json)
performed 28 bounded steps (maximum 30.690 ms) and retained 12 runs. It used
2,833 PUT, 2,623 DELETE, 58 write-phase GET and uploaded 369,528,272 bytes,
versus 2,777 PUT, 2,539 DELETE, two GET and 348,253,673 bytes without
consolidation. Reopen used 17 GET and 86.797 ms, versus 45 GET
and 141.214 ms. Peak RSS was 49,348,608 bytes; the exact query still used
1,292 GET and matched the oracle. One unpaced run per condition does not
establish a latency distribution. The request and byte tradeoff supports
keeping this small-index coalescing step, while the unchanged exact GET count
and retained mixed packs leave M22–M24 acceptance open.

## Mixed-pack reclamation probe

The [no-reclamation run](m22/overwrite-half-baseline/run.json) loads the same
verified 250,000×128 SIFT1M prefix, then overwrites each even ID once with the
declared 137-position rotation. It seals and consolidates after each 64-log
group. The [synchronous prototype](m22/overwrite-half-reclaimed/run.json) and
[staged version](m22/overwrite-half-staged/run.json) use identical input and
reclaim a physical pack when at least half its estimated payload is stale and
at least 64 KiB can be saved. A pack containing a block with no live IDs is
ineligible until the separate index-pruning step drops that block. All three
runs retained 312 objects after cleanup, reopened in 162–167 ms, and matched
the independent exact oracle. These are unpaced targeted probes, not a
distribution for independent read/write arrivals.

| Local MinIO, 250,000 base + 125,000 overwrites | No reclamation | Synchronous | Staged |
|---|---:|---:|---:|
| Visible durable payload | 260,585,324 B | 197,239,968 B | 197,239,968 B |
| Write PUT / DELETE / GET | 4,253 / 3,941 / 90 | 4,497 / 4,185 / 1,060 | 4,497 / 4,185 / 1,060 |
| Uploaded payload | 564,635,080 B | 701,958,774 B | 701,958,774 B |
| Longest reclamation call | — | 134.975 ms per pack | 38.214 ms per step, excluding planner |
| Load wall time | 29.537 s | 37.242 s | 38.847 s |
| Peak whole-process RSS | 53,116,928 B | 53,510,144 B | 53,411,840 B |

The staged path freezes the live IDs for one pack, reads one authenticated
block per call, writes the replacement pack in one call, and publishes one
immutable root in the next. A newer acknowledged log may arrive during staging;
seal and run consolidation wait until root publication, so omitted IDs cannot
become visible from the old block. A failed or uncertain create requires reopen;
unpublished packs are disposable orphans. The 63,345,356-byte reduction costs
137,323,694 extra upload bytes plus 970 GET and 244 each of PUT/DELETE in this
update wave. The staged maximum is below the 100 ms maintenance target, but a
single unpaced maximum is not a p95 and the extra work has not been measured
under the offered independent load. The exact query still needed 1,938 GET,
so selective retrieval remains necessary.

## Fully dead block pruning probe

The [baseline](m22/overwrite-prefix-baseline/run.json) and
[pruning run](m22/overwrite-prefix-pruned/run.json) load the same verified
250,000×128 corpus, then overwrite the first 125,000 IDs once with the same
137-position rotation. Both seal and consolidate after each 64-log group.
The pruning run removes block references with no latest IDs from one <=1 MiB
run index at a time: it publishes a fresh index, then a fresh root, and cleans
packs no longer referenced. A later log may shadow retained IDs while the
plan is staged; seal, consolidation and repacking wait for its root. Index
and root response loss after durable PUT were exercised on disposable MinIO.
The local restart test also covers a run becoming empty. Neither run uses a
cache or selective query path.

| Local MinIO, 250,000 base + 125,000 prefix overwrites | Baseline | Pruned |
|---|---:|---:|
| Visible durable payload / objects | 260,357,414 B / 312 | 174,033,479 B / 211 |
| Write PUT / DELETE / GET | 4,253 / 3,941 / 90 | 4,293 / 4,082 / 100 |
| Uploaded payload | 563,980,570 B | 582,537,421 B |
| Prune plans / longest call including planning | — | 15 / 17.069 ms |
| Load wall time / peak whole-process RSS | 23.866 s / 55,623,680 B | 24.619 s / 52,920,320 B |
| Reopen / exact GET | 21 / 1,938 | 16 / 1,295 |

The 86,323,935-byte durable-payload reduction cost 18,556,851 uploaded
bytes, 40 PUT, 141 DELETE and 10 GET. No mixed-pack repack qualified in this
particular contiguous-update run; the local test covers pruning a dead block
and then repacking the remaining live block. Both measured exact results
matched the independent oracle. The one-run-per-condition result does not
establish p95 or independent-arrival gates. Pruning currently skips an index
larger than 1 MiB, so broader size-tier handling remains required if a future
workload creates such runs.

M22 acceptance still requires the M21 250,000-row write/request/byte/recovery
gates, exact results, and MinIO publication/cleanup crash tests. M23 will
measure cold, NVMe-warm, RAM-hot and cache-pressure cases using this block
identity. M24 will compare selective results with the exact oracle and enforce
the stated quality and cost gates. No AWS test answers a question at this
stage.
