# M31 one-million-vector envelope

## Declared envelope (before any 1M measurement)

Amendment before the first serve measurement: the first attempt failed while
loading. Size-tiered consolidation capped run indexes at 512 KiB, so about 80
runs were needed against the root's 64-run limit and seals stopped with
`MaintenanceRequired`. The M21 profile's 24 MiB sketch budget would also have
refused to open 1,000,000 rows. The cap is now 2 MiB, and the M31 profile
(`SegmentedServingOptions::m31`) is M21 with a 128 MiB sketch budget. No
gate changed.

The corpus is all 1,000,000 base vectors of the TEXMEX SIFT1M archive (the
archive whose SHA-256 `benchmarks/M21.md` records) and the first 200 rows of
its query file: 128 dimensions, squared Euclidean, k=10. As in M21, metadata
marks IDs divisible by 100 (the declared resident 1% predicate), and update
waves overwrite ID `id` with base row `(id + 137 * generation) % 1,000,000`.
The harness, offered load and process split are the accepted M24 ones
(`tools/m24_acceptance.py --rows 1000000`): load in 100-row batches, then 300 s
of four writers each offering one 100-row overwrite batch per second and four
readers each offering one query every 100 ms, then restart, update-wave
quality, cache loss and backup verification in a new process. The serving
options are `SegmentedServingOptions::m31` (M21 plus the sketch budget): 12 blocks, 8 range GETs
and 1 MiB per query, a 256 MiB NVMe cache, no RAM block cache, 4 query
threads.

Every M21 gate applies unchanged except two that scale with resident routing
state, which is about 90 bytes per row at 250,000 rows (22.6 MB of sketches):

| Gate | 250,000 rows (M21) | 1,000,000 rows (M31) |
|---|---:|---:|
| Peak engine RSS | <=64 MiB | <=192 MiB |
| Fresh open and reopen | <=1 s | <=2 s |

The unchanged gates: write p95 <=150 ms; warm unfiltered and filtered query
p95 <=50 ms; cold query p95 <=200 ms; static and update-wave mean recall@10
>=0.90 and 5th percentile >=0.80 for both classes; short results <1%; zero
lost acknowledged writes, overloads and late slots; <=6 PUT/s, <=6 DELETE/s,
<=2 MiB/s upload, <=1 LIST/minute; <=8 GETs and <=1 MiB per cold query;
NVMe cache <=256 MiB; visible payload <=1 GiB; cache loss and backup restore
preserve results; no maintenance errors. The static-quality oracle is an
exact f64 scan of the 1,000,000 rows (ties by ID) generated by the harness's
`oracle` command and recorded with its SHA-256.

The extracted `sift_base.fvecs` (516,000,000 bytes) has SHA-256
`21f66e2975057b5728ba56de1c825bac4f4d89d596609ae985741c6242631816`; its first
129,000,000 bytes match the M21 250,000-row prefix digest, and
`sift_query.fvecs` matches the M21 query digest. The
[oracle](m31/oracle-sift1m-1000000.json) reproduces the recorded 250,000-row
oracle exactly when limited to that prefix, and its unfiltered top-10 sets
match the archive's `sift_groundtruth.ivecs` for 199 of 200 queries; query 93
differs only in an exact distance tie at rank 10, broken here by lower ID.

| Cold query p95 | 78.8 ms | <=200 ms |
| Remote reads per cold static query (p50 / max) | 7 / 8 | <=8 |

Range requests, not bytes, bind: static cold queries read 7 of 8 allowed
requests at the median but at most 0.47 MB of 1 MiB. Raising the block budget
with 8 requests leaves update-wave recall at 0.876 (16 or 24 blocks), and the
best possible 8 blocks hold only 0.885 of the true top-10, while 10 or 12
uniformly chosen requests reach 0.962 and 0.990. At 1,000,000 rows a query's
neighbors spread across more packs from independent seals, so fewer of them
share a request than at 250,000 rows.

## Latency investigation

Admission charges every member of a queued write group for the group's full
execution interval, excluding synchronous `make_room` maintenance. The M24
acceptance `Profiled` wrapper inherited `Engine::apply_requests`'s per-request
fallback: it issued a separate log PUT for each grouped member. This explains
M27's and M31's 1,200 log objects for 1,200 writes and makes the reported write
execution p95 much larger than one serial request. The wrapper now forwards
`apply_requests`; its regression test checks that two requests publish one log.
The engine's existing group acknowledgement, retry and recovery rules apply.

Temporary timing of 401 serial 100-row overwrites on a 100,000-row LocalStore
namespace gave p50/p95 milliseconds: validation and retry state 1.63/2.01,
log encoding 0.57/0.70, durable log create 11.15/16.35, tail apply
0.049/0.105. This does not reproduce the 11.1-to-42.7 ms MinIO write p95
increase. The S3 store code, object-store crate, MinIO image, machine and Rust
version were unchanged between the M24 and M27 runs; the wrapper's grouped
sequential PUTs account for the reported interval. The clean M31 run's idle
maintenance p95 was 30.10 ms (p99 40.49 ms), which adds to the wait of arrivals
during a non-preemptible unit.

`cargo run --offline --release --example m31_latency_probe -- 1000000 30 8 MODE`
uses a deterministic synthetic 128-dimensional corpus, an in-memory object
store, and the acceptance arrival pattern: four 100-row writers each second and
four readers each 100 ms, with half the reads unfiltered. Use `legacy` for
the old wrapper fallback or `grouped` to forward group commit. The matched
30-second runs (8 routing threads, no block cache or network) measured:

| 1M-row probe | Original routing, grouped | Faster routing, grouped | Faster routing, legacy |
|---|---:|---:|---:|
| Log objects / 120 writes | 39 | 40 | 120 |
| Write execution p95 (ms) | 5.82 | 5.68 | 5.95 |
| Unfiltered execution p95 (ms) | 25.09 | 23.50 | 17.12 |
| All-query queue p95 (ms) | 49.87 | 46.95 | 39.25 |
| Unfiltered end-to-end p95 (ms) | 64.35 | 59.54 | 54.48 |

Temporary routing timing in a yield-paced version of this probe measured
routing p50/p95 12.19/14.88 to 10.66/12.90 ms; reranking was about
0.56/0.91 ms p50/p95. The change decodes complete five-bit groups directly
while preserving f64 scores and safe prefix pruning. Four simultaneous reads,
write publication and idle maintenance still serialize through admission, so
the short in-memory runs vary and do not establish a MinIO gate result. A
16- and 32-thread in-memory runs after the change reached 56.26 and 54.36 ms
unfiltered p95, so the profile remains at 8 threads. No MinIO rerun was
possible here: Docker API access was denied.

## Concurrent queries (M34)

The same probe compared `origin/main` (`73d0c5a`, queries on the committer)
with M34 (queries on `Limits::queries` = 4 reader threads, 8 routing threads
each): `m31_latency_probe 1000000 30 8 grouped [4]`. Apple M4 (10 cores,
16 GiB), macOS, rustc 1.98.1, in-memory store, 30-second runs. Other builds
shared the machine (load average 5-11 at run start), so the runs alternate
main and M34:

| 1M-row probe, interleaved runs | main | M34 |
|---|---:|---:|
| All-query queue p95 (ms) | 39.18 / 39.88 / 47.01 | 6.69 / 2.35 / 4.08 |
| Unfiltered execution p50 (ms) | 11.76 / 11.96 / 12.11 | 40.77 / 44.66 / 43.08 |
| Unfiltered execution p95 (ms) | 18.70 / 20.19 / 23.27 | 62.59 / 52.87 / 51.80 |
| Unfiltered end-to-end p95 (ms) | 53.22 / 54.68 / 59.41 | 66.88 / 52.99 / 52.17 |
| Write execution p95 (ms) | 5.49 / 5.67 / 5.91 | 6.69 / 7.15 / 6.74 |

Queries no longer queue behind writes and maintenance, but the end-to-end p95
did not improve and the 50 ms gate is not met. The four readers submit
together every 100 ms, and routing one query costs about 10 ms on 8 cores, so
four simultaneous queries share the CPU for about 40 ms either way. With one
reader thread (`... 8 grouped 1`) the queue p95 was still 39.91 ms, so most
of main's queue wait was this burst, not the committer. Fewer routing threads
per query did not help: 4 readers with 2, 3 or 1 threads measured 56.61 and
98.79, 63.08, and 77.76 ms end-to-end p95 (load average 7-15). Meeting the
gate on this arrival pattern needs cheaper routing per query, not more
concurrency.

## Published-view memory (M34)

`m31_latency_probe 1000000 3 8 grouped 4` (deterministic synthetic
128-dimensional vectors, in-memory store, macOS arm64, rustc 1.98.1) with
`M31_PROBE_SNAPSHOT=1`, which holds an old view through 32 sequential 100-row
overwrites and a seal. Before this change a root publication copied the whole
latest-ID directory (24 bytes per ID) while a reader held the previous view:
process RSS rose 23.89 MiB at that publication. With the directory in shared
1,024-slot pages that copy only the pages a seal changes, the rise is
0.91 MiB. Large merges at open rebuild pages linearly, releasing each old page
as it is consumed.

The full [paged-directory acceptance](m31/acceptance-minio-1m-paged-directory/run.json)
did not reproduce the isolated RSS win. Against the
[M33–M36 main run](m31/acceptance-minio-1m-m33-m36/run.json), load peak RSS
was 123.33 versus 67.73 MiB, while serving RSS immediately after open was
152.17 versus 152.81 MiB. Serving then rose to 226.14 versus 192.53 MiB;
the excess arose during the five-minute read/write and maintenance phase,
not the initial open or the later verification process. The original paged
`retain` allocated a fresh buffer for every changed page even when that page
was uniquely owned; under a published view it allocated one buffer per changed
page. Consolidation, pruning and reclamation can change locations across much
of the directory. This made the 24 KiB page buffers a high-churn allocation
pattern. The first open took 1.708 versus 1.480 seconds with identical 668 GETs
and 192.07 MB of payload; the later reopen took 2.081 versus 1.413 seconds,
but also issued 669 versus 648 GETs on different post-serve roots. Those two
runs alone do not isolate directory CPU time from backend and maintenance
variation.

Main's serving RSS was 155.06 MiB after static quality and 192.53 MiB at its
peak. The 1M held-view in-memory probe measured a 25.99 MiB live-heap rise
across a root publication with the single-vector directory, including its
23.89 MiB directory copy. The root, tail and sketch set are also shared with
readers: writes copy tail nodes and sketch liveness, and sketch compaction can
copy one pack's sketch. The directory copy explains most of the measured
28.5 MiB peak-RSS increase over the pre-M34 acceptance, though the two runs
do not isolate every remaining byte.

Follow-up probes used `m31_latency_probe 1000000 300 8 grouped 4` with
`M31_PROBE_LOCAL=1` and `--features memory-probe`: deterministic synthetic
128-dimensional vectors, a fresh temporary LocalStore namespace per run,
macOS arm64, rustc 1.98.1. Replacing only the directory implementation with
main's flat vector gave 217.33 MiB peak RSS and 164.38 MiB peak requested
heap. Bounded groups of 1,024-slot pages (at most 16,384 slots per backing
allocation) gave 209.20 and 156.03 MiB. Both runs completed 1,200 writes and
the scheduled queries; warm unfiltered end-to-end p95 was 57.86 versus
57.83 ms. The local synthetic workload itself exceeds 192 MiB on both
layouts, so its absolute RSS is not the MinIO acceptance.

The subsequent clean [grouped-page MinIO run](m31/acceptance-minio-1m-grouped-pages/run.json)
peaked at 202.98 MiB RSS, versus 193.84 MiB in the clean
[main-after-M37-stage-3 run](m31/acceptance-minio-1m-main-after-m37s3/run.json).
Both used the same SIFT1M corpus, loopback MinIO image, Apple M4 and rustc
1.98.1; both failed the 192 MiB gate. Their open reads were identical (668 GETs,
192.07 MB payload), and open time was 1.194 versus 1.209 seconds. The MinIO
result does not reproduce the local synthetic RSS gain, so this change has no
demonstrated M31 memory-gate improvement. These two runs alone do not isolate
the cause of the RSS difference.

With `M31_PROBE_REOPEN=5` on the same 1M in-memory namespace, main's flat
directory reopened in 0.376, 0.323, 0.336, 0.322 and 0.309 seconds. Bounded
pages initially took 0.489, 0.447, 0.423, 0.420 and 0.395 seconds. Keeping
page-end IDs in a contiguous array changed those times to 0.330, 0.309,
0.303, 0.301 and 0.298 seconds. This isolates a page-lookup cost during
recovery; it does not include MinIO request latency.
