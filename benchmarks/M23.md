# M23 bounded disposable block-cache probe

Status: experimental RAM/NVMe block caching is implemented for
`experimental-segmented` exact and point reads. Correctness, loss and pressure
checks pass on local storage and disposable MinIO. The declared 250,000-row
latency, request and workload gates remain unaccepted; exact full scans need
M24 selective retrieval.

## Cache contract

`SegmentedDatabase::with_block_cache` attaches a cache after authoritative
object-store open and recovery. Each entry is named by a versioned hash of the
immutable object key, offset, length, complete payload length and committed
block digest. RAM and NVMe hits check the selected root's length, SHA-256 and
block fields before use. Corrupt or missing cache bytes cause one authoritative
range fetch; invalid or missing authoritative bytes fail the read. The cache
does not acknowledge writes, publish roots or participate in recovery.

The cache owns only `glider-block-cache-v1` below the configured directory.
Opening inventories and trims that directory to the NVMe budget without
loading vector payloads. A cache mutex serializes block fetch/validation, so
this experimental path has at most one in-flight block read per database
handle. If the directory is unavailable, reads continue through RAM and S3
and stats mark NVMe unavailable. The configured byte charges include conservative per-entry overhead;
process RSS and on-disk occupancy must still be measured. Cache file writes
need no durability guarantee. Reopening after total directory loss starts from
the selected S3 root and refetches blocks. A selected root with a missing pack
is rejected at open even if cache files remain.

## Targeted 250,000-row result

The [raw run](m23/cache-probe-250k/run.json) uses the verified M21 SIFT1M
250,000×128 prefix and first query, squared Euclidean, k=10, consolidated
segmented runs, 4 MiB RAM and 256 MiB NVMe cache budgets. It ran on Apple
M4/macOS 26.6.2 with the pinned local MinIO image and Rust release build.
The runner verifies both dataset hashes, compares every pass to the independent
exact oracle from the load phase, and removes the MinIO container and local
cache directory. “Cold” means an empty **engine** cache; this run does not
flush the host OS page cache or MinIO's storage cache. “NVMe-warm” means a
new database process using the retained cache directory. RAM-hot is one
repeated point read, not a hot full-query claim.

Reproduce it with `python3 tools/test_s3.py --segmented-cache NEW_OUTPUT --data DATA_DIRECTORY`,
using the verified prefix and query files from M21.

| One exact query or point read | Wall time | Query S3 GET | Remote block payload | Cache observation |
|---|---:|---:|---:|---|
| Empty engine cache | 3,455.984 ms | 1,292 | 167,206,780 B | 1,292 remote fetches |
| NVMe-warm fresh process | 1,005.487 ms | 0 | 0 B | 1,292 NVMe hits |
| Point read after warm scan | — | 0 | 0 B | 1 NVMe hit |
| Repeated point read | — | 0 | 0 B | 1 RAM hit |
| After total cache deletion | 3,327.060 ms | 1,292 | 167,206,780 B | exact result unchanged |
| 256 KiB NVMe pressure, first/second scan | 3,230.654 / 3,299.966 ms | 1,292 / 1,292 | 167,206,780 B each | no cache hits |

The full scan occupied 172,990,464 charged NVMe bytes in 1,292 entries and
4,170,190 charged RAM bytes in 33 entries, below the configured budgets.
The pressure scan occupied 147,456 charged NVMe bytes and zero RAM bytes.
Peak whole-process RSS in the cache probe was 41,025,536 bytes; the separate
fresh warm process reached 39,731,200 bytes and the load probe reached
50,921,472 bytes. Fresh-process open took 142.760 ms with 14 GET cold and
87.821 ms with 14 GET warm; these are metadata/index reads,
reported separately from query GET. These are one-query diagnostics, not p95
or independent read/write traffic. Remote byte counts are authenticated block
payloads, not HTTP envelope or billed transfer bytes.

The M21 cold target is <=8 GET, <=1 MiB and <=200 ms per query; the exact
scan exceeds all three. The NVMe-warm target is <=2 GET, <=256 KiB and
<=50 ms; remote work passes but 1,005 ms latency does not. Additional
selective candidate generation and bounded metadata are necessary before
M23/M24 acceptance. Per-request deadline integration and independent concurrent
reader admission are also pending. No AWS measurement is needed for this cache
decision.
