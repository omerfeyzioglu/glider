# M16 concurrent admission acceptance

Status: the targeted local MinIO pair passed all declared budgets; final PR CI
is pending.

The serial API has no queue/memory limits for concurrent callers. Compare a
caller mutex around `SingleMachine` with a bounded FIFO and one commit worker.
The change addresses admission correctness; it does not add concurrent writers
or claim lower storage latency. Keep explicit caller batches: no measurement has
identified group commit as necessary.

The targeted workload retains M8's 2,000 rows, 64 dimensions, squared Euclidean
metric, seed 42 and k=10. Four clients each submit one 100-mutation batch and ten
queries per second, for 50 seconds: 200 writes, 2,000 distinct queries and 400
logical mutations/s offered. Half the queries use the 1% equality filter. Check
exact results against the committed boundary and verify final state after reopen.
Use one paired run on the same pinned loopback MinIO, recording revision, source,
environment, raw samples, request/byte counts and process RSS. CI smoke tests are
correctness evidence only. No AWS run is needed for this queue decision.

Predeclared limits: eight outstanding commands (including active work), 320 KiB
of encoded admitted payload; reject overload immediately. Client end-to-end p95
includes admission, queue wait, maintenance, execution and response delivery:
write <=150 ms, each filtered/unfiltered query class <=50 ms. Queue wait p95
<=75 ms separately for writes and queries; batch execution excluding
maintenance p95 <=100 ms, maintenance p95 <=100 ms; sustained acknowledged
throughput >=350 logical mutations/s and peak RSS <=64 MiB. Measure maintenance
separately and retain the original serial M8 timing definitions. These are
workload acceptance limits, not a production p99 or an arbitrary-load guarantee.

Overload, cancellation, shutdown, worker panic and uncertain publication require
deterministic failure tests. A cancellation accepted while queued prevents
publication; once execution starts, the outcome is resolved with the M15 ID.
No successful acknowledgement precedes durable publication. M17/M18 decisions
will use the read and maintenance measurements from this same run. Recovery retains M8's <=500 ms, <=64 GET and
<=4 LIST bounds. Arrival lateness is reported separately, including a query
whose client was still waiting for its preceding batch.

`python3 tools/m16_benchmark.py NEW_OUTPUT` runs the fixed pair. `--smoke` uses
two unpaced rounds, verifies exact/recovered state and makes no tail-latency
claim. Each write updates 100 IDs in the caller's disjoint 500-ID range; query
results are checked against a separate model replayed in returned commit order.
Generator: `splitmix64-id-generation-v1`. Request body byte counts exclude
responses, headers and TLS. RSS includes setup, retained samples and oracle
validation. The caller mutex baseline has no overload bound; it is only a
comparison under the declared four-client workload.

The fixed-workload payload preflight finds a largest four-client burst of
305,455 encoded bytes (including conservative nonce/boundary widths). The
320 KiB byte limit accommodates that burst; count and RSS limits remain separate.


## Measured result

Both modes passed on Apple M4/macOS 26.6.2, Rust 1.98.1 release, Docker 29.1.3,
using the pinned MinIO image. [Environment/source identity](m16/run.json): dirty
parent `cf31d915`, source SHA-256 `77f2cd1db7abaed978359e732255497888c2d3ab9714eb6bc46034ed9304fc10`.
Each mode ran in its own process against a fresh namespace in the same container.

[Mutex raw samples](m16/mutex.json), [worker raw samples](m16/worker.json).
Each phase checked 2,000 distinct exact queries and recovered all final vectors
and metadata. Recovery used 13 GETs and two LISTs. Each measured serving phase
used 212 PUTs, 205 DELETEs (including graceful owner release), 12 LISTs, zero
GETs and 33,623,262 request-body bytes; no HTTP/transport errors occurred.
The twelve maintenance events per phase are limited observations, not a stable
production tail estimate. Client arrival-lateness p95 was 29.891/31.353 ms;
queries scheduled immediately after a batch can start late while that client
waits for its batch. Offered workload and attained throughput are reported
separately. The entire MinIO container was removed successfully after both runs.

The FIFO makes early queries wait behind already admitted batches, explaining
its higher filtered-query tail relative to the caller mutex. Both remain within
the declared read budget. The worker is selected for explicit bounds, FIFO order,
cancellation and failure semantics, not a latency improvement. No group commit,
pinned read view or background maintenance is justified by this run. Conditional
M17/M18 decisions must retain this workload scope; write-queue p95 is close to
its limit, so larger load needs new capacity evidence.

Six deterministic admission tests cover count/byte overload, release before reply,
queued cancellation/drop, in-flight cancellation, FIFO batch/read visibility,
duplicate outcomes, drain/cancel shutdown, worker errors/panics and isolated
recovery. The payload preflight and full all-feature test suite passed locally.
Routine CI uses only the short MinIO comparison smoke.
