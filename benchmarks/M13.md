# M13 serial serving validation

Status: measured acceptance passed for the M8 envelope. Merge is gated on final CI.

## Admission bottleneck and layout decision

The initial paced run used M10's 128 KiB chunked snapshots. Its first five-minute
segment (300 cycles, 30,000 queries, 120,000 logical mutations) measured batch
p95 **112.44 ms**, above the 100 ms batch-admission budget. That attempt was
stopped; it is not a completed soak. [Raw first segment](m13/chunked-epoch0.json).
The source was revision `8753def` (full source hash is in the raw report), Rust
1.98.1 release on Apple M4/macOS with the pinned loopback MinIO image used by
`tools/m13_soak.py`. Process RSS peaked at 14.89 MiB. Query p95 was 0.205 ms
unfiltered and 0.034 ms filtered; recovery and takeover were within budget.

Chunked compaction publishes twelve chunks and a manifest, then removes old
chunks and covered mutations. The M8 resident serving path does not need the
streaming layout. M10 had already measured single-object snapshots within its
memory/recovery limits. Selecting one full snapshot replaces twelve chunk PUTs
plus a manifest PUT with one PUT, and twelve old chunk DELETEs plus root DELETE
with one root DELETE. It preserves existing versioned formats and publication
semantics. Optional chunking remains available for streaming consumers.
The targeted post-change evidence is the same paced workload below; no broader
benchmark is needed to decide this small-envelope layout.

## Workload and measurement definitions

The runner uses the M8 2,000-row, 64-dimensional, seed-42 workload and k=10.
Every cycle performs 100 fresh queries and four atomic 100-operation batches:
200 overwrites, 100 deletes and 100 inserts. It paces at one cycle/second. M12
selects explicit exact serving, so the query mix is 60% unfiltered and 40%
`selected=true` (every 100th ID); ANN requests are separately rejected.

Each query is checked against an independent full-sort oracle, outside the
measured query interval. Every process reconstructs all preceding mutations
from deterministic inputs, then verifies every recovered vector and metadata
value, row counts, exact distances and ties. Six successive processes run
300 cycles each. The first injects a lost cleanup acknowledgement, abandons the
poisoned owner, stages an isolated takeover, then exercises backup and restore.
M9 tests cover abrupt process exits at underlying publication boundaries.

Query timers measure the API call, excluding oracle preparation. Batch timers
include input validation, synchronous due maintenance and durable publication;
batch time divided by 100 is not a client's latency. The original single-write
budget remains separate. Open timers include ownership acquisition and recovery;
HTTP counters include owner-control reads/listings. Takeover/restore timers
include staging, new-owner open and exact-state validation. RSS is each process's
lifetime high-water mark. Visible engine-object counts exclude two ownership
objects. Mutation and maintenance bytes are logical payloads, not HTTP/device
bytes; backup destination copies are excluded from routine maintenance writes.
Raw latency arrays preserve sample order. OS cache, service cache, CPU power and
competing load are uncontrolled; these results do not establish cloud latency or
concurrent request queue latency.

## Reproduce

`python3 tools/m13_soak.py target/m13-run` provisions a disposable MinIO service
and records all epoch samples plus environment. `--smoke` uses two short unpaced
processes and is a CI correctness/request-count gate. The complete run checks
query p95 <=5 ms, batch p95 <=100 ms, >=100 logical mutations/s, every open <=500
ms with <=64 GETs and <=4 LIST pages, takeover <=30 s, RSS <=64 MiB, <=128 visible
objects including ownership and additional maintenance payload <=2x mutation payload.

Six serving unit tests cover pre-I/O capacity validation, failed scheduled
maintenance before mutation publication, uncertain batch atomicity, poisoned
close, interrupted backup with a writable source, restoration and legacy v1/v2
to optional v3 chunked migration. The full prior test suite and all-feature
Clippy passed; final CI remains required for the selected implementation.
