# M39 in-region AWS acceptance

## Per-seal layout on a free-tier instance

[Raw result](m39/aws-1m-per-seal/run.json): `tools/aws_acceptance.py --rows
1000000` at revision `f735f3a` (main with M33–M37 stage 3 plus this runner),
the M31 envelope against S3 Standard in eu-central-1 from an
`m7i-flex.large` (2 vCPU, 8 GiB; the only types this account's free plan
allows are burstable 2-vCPU instances). The instance built the revision,
read the SHA-verified SIFT files from the test prefix, ran load, serve and
verify, uploaded the result, deleted its namespace and terminated itself in
about 18 minutes; no run objects remained.

| Measure | AWS m7i-flex.large | MinIO, Apple M4 (`93c21d9`) | Gate |
|---|---:|---:|---:|
| Lost acknowledged writes; cache loss; backup restore | 0; equal; equal | same | pass |

| Open / reopen | 6.96 / 6.20 s | 1.48 / 1.41 s | <=2 s |
| Warm unfiltered query p95 (execution p50) | 173.0 ms (145.5) | 45.9 ms (36.0) | <=50 ms |
| Cold unfiltered query p95 | 232.7 ms | 51.9 ms | <=200 ms |
| Filtered query p95 | 12.8 ms | 3.2 ms | <=50 ms |
| Write p95 | 262.3 ms | 33.1 ms | <=150 ms |
| Peak engine RSS | 277.3 MiB | 192.5 MiB | <=192 MiB |
| Static recall@10 first / warm pass | 0.955 / 1.000 | 0.955 / 1.000 | >=0.90 |

Correctness holds on S3 Standard. Query execution, not waiting (queue p95
21.7 ms), dominates query latency: routing scores the sketches of all
1,000,000 rows, which two burstable vCPUs cannot do within the gate. The
clustered view (M37) scores only the probed clusters' rows and is the next
in-region measurement. Open time and RSS are also higher than on MinIO; both
need attribution before conclusions.


## Clustered view on the same free-tier instance

[Raw result](m39/aws-1m-clustered/run.json): `tools/aws_acceptance.py --rows
1000000 --clustered` at `7a4cd95` (M37 complete, 32 probes in the M31
profile, S3 read retries). An earlier clustered attempt at `37e9757` failed
at the start of serving on a GET that hit a pooled connection S3 had closed
(`IncompleteMessage`) with no read retry; idempotent reads now retry (PR #96).
This run needed no retries. The instance terminated itself and no run objects
remained.

Recall, durability and cold latency meet their gates on S3 Standard. Warm
latency, writes and open time stay CPU-bound on two burstable vCPUs (query
execution alone is 93.5 ms at the median, against 25 ms on the 10-core
laptop for the same revision family), so the in-region latency gates need a
larger instance, which this account's free plan does not allow. RSS exceeds
the gate on both layouts.

## Clustered view on an 8-vCPU instance

[Raw result](m39/aws-1m-clustered-c7g/run.json): the same clustered run at
`af7fb0e` (main) on `c7g.2xlarge` (8 Graviton3 vCPU, 16 GiB) after the
account moved to a paid plan; credits still covered it. No read retries were
needed; the instance terminated itself and no run objects remained.

On S3 Standard with comparable CPU, query latency and quality meet the M31
gates: warm p95 29.4 ms, cold p95 57.1 ms, recall 0.998 static and 0.966
after updates. The remaining in-region gaps are S3-specific: open and reopen
take seconds because opening reads many index and sketch objects (each a
round trip), write p95 follows conditional-PUT tail latency, and RSS stays
above the gate as on MinIO.
