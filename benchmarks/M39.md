# M39 in-region AWS acceptance

## Per-seal layout on a free-tier instance

[Raw result](m39/aws-1m-per-seal/run.json): `tools/aws_acceptance.py --rows
1000000` at revision `f735f3a` (main with M33–M37 stage 3 plus this runner),
the M31 envelope against S3 Standard in eu-central-1 from an
`m7i-flex.large` (2 vCPU, 8 GiB; the only types this account's free plan
allows are burstable 2-vCPU instances). The instance built the revision,
read the SHA-verified SIFT files from the test prefix, ran load, serve and
verify, uploaded the result, deleted its namespace and terminated itself in

in-region measurement. Open time and RSS are also higher than on MinIO; both
need attribution before conclusions.

## Root manifests (root v5): publication bytes in the update-wave replay

The clustered runs above uploaded about 40% of their bytes as roots, because
every root embedded every block reference. Root v5 (DESIGN.md, "Root
manifests") names each run's block list through an immutable run manifest
and rewrites only changed runs' manifests. This replays the 1,000,000-row
M37 update wave in memory, before and after the change, with
`m37_conversion_probe` (which now also times a reopen of the final namespace
and counts the whole-object GETs it makes by key kind):

```
cargo build --release --example m37_conversion_probe
m37_conversion_probe sift_base.fvecs sift_query.fvecs 1000000 - 300
```

Dataset: the SIFT1M base file (SHA-256 `21f66e29…`, the M31 corpus) and the
first 200 queries, loaded in 100-row requests with M21 one-percent
metadata, converted with default options (256 centroids), then 300 rounds of
the M31 update wave (400 overwrites per round as two group-commit logs,
idle maintenance to completion each round; one round is about one second of
the M31 envelope). Store: in-memory complete-object store. Before: engine at
`8a12677` (main) with the probe change; after: this branch. Apple M4 (10
cores, 16 GiB), macOS, release build, while other builds ran (load average
7 to 33). Raw results: before
[1](m39/root-manifests/before-1.json) [2](m39/root-manifests/before-2.json)
[3](m39/root-manifests/before-3.json), after
[1](m39/root-manifests/after-1.json) [2](m39/root-manifests/after-2.json)
[3](m39/root-manifests/after-3.json); runs 2 and 3 alternated before and
after. Object counts and bytes are identical across the three runs of each
build.

| Measure (300 rounds) | Before (root v4) | After (root v5) |
|---|---:|---:|
| Root creates; root bytes | 109; 245,401,227 | 109; 23,939,715 |
| Run manifest creates; bytes | — | 119; 3,594,608 |
| Bytes per root publication (root + its manifests) | 2,251,387 | 252,608 |
| All uploaded bytes | 529,096,888 | 311,229,984 |
| Uploaded MiB per round | 1.68 | 0.99 |
| Selected root at the end (19 runs, 9,897 blocks) | 2,673,898 B | 220,489 B |
| Reopen: root and manifest GET bytes (GETs) | 2,673,898 (1) | 945,305 (1 + 19) |
| Reopen time, in memory (runs 1/2/3) | 518 / 562 / 1,146 ms | 710 / 550 / 561 ms |
| Maintenance time (runs 1/2/3) | 6.9 / 7.3 / 7.1 s | 14.8 / 7.1 / 7.4 s |
| Recall@10 after the wave (16 probes, 8 req, 1 MiB) | 0.968 | 0.968 |

Other kinds are unchanged: logs 76.8 MB, packs 126.7 MB, indexes 66.4 MB,
catalogs 13.8 MB (36 creates). The 119 manifests are one per seal (18),
consolidation (20) and prune (33), and 48 for runs whose blocks reclamation
moved (20 rounds); posting merges wrote none. Each adds one maintenance step.
Root and manifest bytes fall from 46% to 9% of uploads. The remaining v5 root
is mostly the bounded retry state (at most 128 receipts and 12,800 revision
pairs): by format arithmetic the 19 run entries are only about 6 KB, so it no
longer grows with blocks. Reopen in memory is dominated by the 196.5 MB of
sketch range reads (803 reads, unchanged) and does not separate the builds
under this load; on S3 the root read shrinks to 220 KB plus 19 manifests in
two batched rounds of at most 16. The first v5 maintenance time is an
outlier under load; runs 2 and 3 agree with the baseline. No S3 run was made
for this change.

## Emulated S3 open latency probe

`cargo run --offline --release --example m39_open_probe -- 1000000 20 100`
builds a deterministic 1,000,000-row, 128-dimensional synthetic namespace in
memory (xorshift vectors, 100-row requests, seals and consolidation, then a
256-centroid clustered conversion). Delays are enabled only for open: each
LIST, whole-object GET and range GET waits 20 ms plus returned bytes at
100 MiB/s **per request**. Batches issue independent reads concurrently. The
host was macOS arm64; these are single release runs, not AWS S3 measurements.

| Probe revision | Open ms | Requests | Read MB | List + metadata ms | Root + manifests ms | Run indexes ms | Routing ms |
|---|---:|---:|---:|---:|---:|---:|---:|
| Baseline: 2 index / 8 sketch reads in flight, 256 KiB prefix | 3,344 | 730 | 193.1 | 50 | 85 | 450 | 2,758 |
| 16 in flight, 512 KiB prefix | 2,172 | 730 | 327.2 | 51 | 91 | 156 | 1,874 |
| 16 in flight, 256 KiB prefix | 2,647 | 730 | 193.1 | 57 | 102 | 191 | 2,296 |
| 32 in flight, 256 KiB prefix, uncached | 1,445 | 730 | 193.1 | 57 | 108 | 120 | 1,160 |
| 32 in flight, first cache fill | 1,793 | 730 | 193.1 | 50 | 108 | 211 | 1,424 |
| 32 in flight, same-machine cache reopen | 912 | 26 | 1.1 | 61 | 104 | 157 | 585 |

Tail replay was empty in this fixture (under 0.03 ms each open). In the final
uncached run, routing comprised 58 ms for centroid/catalog load, 955 ms for
sketch frames (687 ms waiting for range batches and 267 ms decoding), and
147 ms for remaining routing build work. Run indexes spent 42 ms in GET batches
and 77 ms in validation/merging. The warm cache reopen spent 66 ms on the
catalog, 380 ms loading cached sketches, 139 ms on routing build and 157 ms on
cached indexes; it issued no index or sketch GETs. Its cache held 704 entries
charged at 130.8 MB. The remaining 26 requests were listing, metadata, root,
21 manifests, centroids and catalog. The 512 KiB prefix made no request savings
in this fixture and nearly doubled bytes, so the final prefix remains 256 KiB.
The 2-second gate is met in this emulation for both final cold and warm opens;
an AWS measurement is still required for the S3 gate.
