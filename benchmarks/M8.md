# M8 initial single-machine envelope

This is the first **small single-namespace deployment target**, not a capacity
claim for larger or real embedding datasets. It uses one writer, an object store
with the contract in `DESIGN.md`, and explicit exact or IVF queries. Reassess the
limits with representative data before deploying a larger collection.

## Workload and acceptance budgets

The initial live set is 2,000 documents of 64 finite `f32` dimensions with
squared Euclidean distance and `k=10`. The deterministic initial input has
uniform vectors; a second 16-cluster input checks whether the ANN quality
decision changes with vector structure. The
`selected=true` metadata key is present on every 100th ID (1% selectivity) and
absent on others. This simple Boolean cardinality is the initial filter target;
more keys and correlated filters require another envelope. Use seed 42, 1,000
independent queries (query seed `42 XOR 0xd1b54a32d192ed03`), and the existing
SplitMix64 generator. A serving cycle assumes 10% overwrites, 5% deletes and
5% inserts relative to live size; the separate long-tail stress case uses 2,000
round-robin puts over 200 live IDs without maintenance. The planned query mix is
50% unfiltered exact, 40% selective filtered exact and 10% explicitly requested
ANN. These rates and the mix are design inputs for M13, not measured traffic.

Budgets below are chosen acceptance limits for this small workload, not measured
results. Latency limits apply to the loopback MinIO/local test environment and
must be re-established for a chosen remote S3 service. Use at least 1,000
distinct queries for query-tail checks; independent full runs are needed before
claiming a stable p99 in production.

| Boundary | Acceptance budget |
|---|---|
| Resident exact search | p95 at most 5 ms for unfiltered and 1%-selective queries; exact IDs and ties match the independent oracle |
| Acknowledged single write | MinIO p95 at most 10 ms and at least 100 operations/s; local p95 at most 30 ms |
| Recovery with 2,000-mutation stress tail | p95 open at most 500 ms, at most 64 remote GETs and 4 LIST pages; peak process RSS at most 64 MiB |
| Routine maintenance | at most 128 visible objects after cleanup; at most 2 times the input mutation payload in additional logical maintenance writes; no acknowledged-state loss after interruption |
| Selective exact on persisted chunks | p95 at most 100 ms, at most 4 GETs and 256 KiB logical bytes per query; no false negatives; nonselective p95 regression at most 20% against the same-format full scan |
| Persisted ANN, when enabled | p95 at most 100 ms, at most 8 GETs and 512 KiB logical bytes per query, mean filtered recall@10 at least 0.90, fewer than 5% short results; otherwise use the exact path |
| Serving soak | 30 minutes with the stated mix, interrupted maintenance and restart; all acknowledged writes and exact results survive, within the same resource limits |

## Targeted baseline

local APFS and a disposable loopback MinIO container (`RELEASE.2025-10-15T17-29-55Z`,
image digest and environment in each S3 raw report). Revision
`8791ebcfaae4af118118c1251704797c2e406aa6`, seed 42. One warm query pass
precedes each timed search; the 1,000-query runs have one timed pass. Timings
include result allocation and timer overhead. Recovery has one untimed reopen
then three timed reopens, so its p95 is just the slowest of three samples.

lifetime high-water mark, including setup. Local and MinIO latency numbers are

## Bottlenecks and next decisions

- **Correctness/ownership (M9):** the existing single-writer rule is a caller
  precondition; enforce and test the deployment boundary before serving writes.
- **Listing and recovery (M10):** the 2,000-object tail costs 2,001 GETs, three
  MinIO listing pages and 0.93 s warm open. It exceeds the restart budget. The
  1.60 MB payload is small relative to the request count. Measure listing,
  replay and snapshot components separately before changing the catalog.
- **Write-side object count (M10):** every single mutation creates one object.
  The benchmark does not measure compaction write amplification or temporary
  coexistence, so those require a targeted M10 measurement.
- **Memory and CPU:** the measured query process RSS stays below 64 MiB and
  resident exact p95 stays below 0.05 ms on the main uniform paths. Neither is
  the first optimization target at this scale. The 1,000-query unfiltered run
  uses more setup memory than the 100-query pilot; do not extrapolate an RSS
  slope from these two points.
- **Selective remote reads (M11):** the resident query baseline makes zero GETs.
  It cannot establish streaming exact cost. Measure chunk GETs and bytes against
  this same filter before choosing summaries or postings.
- **ANN quality (M12):** 8/32 IVF probes violate the quality and fill budgets
  on both uniform and clustered filtered inputs. Keep exact as the supported
  sparse-filter path. Do not choose an automatic ANN planner from the small
  latency differences.

Reproduce the search inputs with the documented `cargo bench --locked --bench
baseline -- --scenario search` harness, `--rows 2000 --dimensions 64 --seed 42
--queries 1000 --samples 1 --k 10 --filter-every 100`, optionally
`--distribution clustered` and `--ivf-partitions 32 --ivf-probes 8
--ivf-iterations 8`; use `--features s3 --backend s3` and the isolated MinIO
setup in `BENCHMARKS.md` for S3. Recovery uses `--scenario recovery --rows 200
--mutations 2000 --samples 3`; commit uses `--scenario commit --operations
100`. Raw JSON contains the full configuration, fingerprints, source hash,
environment, timings, CPU, RSS, answers and storage counters. The backend
checks in CI remain correctness checks, not latency gates.
