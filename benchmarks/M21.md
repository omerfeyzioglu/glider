# M21 large-data workload and decision protocol

Status: accepted after [PR #54 CI](https://github.com/omerfeyzioglu/glider/actions/runs/36412910918)
passed and the PR merged. This accepts the M21 workload/decision milestone;
the larger-than-RAM serving envelope remains unaccepted.
The 5,000 × 128 local MinIO acceptance is recorded in [M20](M20.md).

## Selected workload and gates (declared before the M21 run)

The capacity target is one 250,000-row, 128-dimensional squared-Euclidean
collection, exact and ANN k=10, with 1% equality-filter membership. Its raw f32
vectors alone occupy 128,000,000 bytes, exceeding the fixed 64 MiB engine-RAM
budget. Use a fixed 256 MiB disposable NVMe cache. The selected corpus is the
first 250,000 base vectors of the primary [TEXMEX SIFT1M archive](ftp://ftp.irisa.fr/local/texmex/corpus/sift.tar.gz)
and its separate query file. The archive SHA-256 is
`92f1270c5e3a0cb46b89983e72b0511e4df065c31a9fa0276d8c9b1fca5bc81a`;
the 129,000,000-byte base prefix SHA-256 is
`fab6b3f6c68d8bca09c72b0ee84a8126b80aebc635765fb52c0ab3efbda51960`,
and the 5,160,000-byte query file SHA-256 is
`f7fc9be140accdfd64116c2fa2365ecdb69b8f084970c6b0532db5ff79ac8fdc`.
Use the first 200 query rows for later acceptance and rotate overwrite values
by `(id + 137 * generation) % 250000`; metadata marks IDs divisible by 100.
This is a proposed envelope, not an accepted one. The M21 attribution step
uses the previously verified SIFTsmall
10,000-row prefix and 100 held-out queries from M19, with the same deterministic
137-position overwrite rotation. The selected SIFT1M subset avoids treating a
repeated 10,000-row corpus as ANN quality evidence at 250,000 rows.

Four independent writers each offer one atomic batch of 100 overwrites per
second. Four independent readers each offer one query every 100 ms, alternating
filtered and unfiltered. This totals 400 offered mutations and 40 queries per
second. Query arrival does not depend on a preceding write acknowledgement.
Each producer keeps at most one request outstanding; a slot more than one
period late is skipped, and admission overload is counted without retry.
Report both kinds of loss, arrival lateness, queue time, execution time,
maintenance time, request counts, bytes, RSS, recovery and exact-oracle checks.
Request IDs and final-state verification preserve the existing conditional
write/recovery contract. The 20-second diagnostic is a boundary observation,
not a tail-latency or larger-than-RAM acceptance run.

At the 10,000-row diagnostic, compare against the existing local MinIO gates:
zero overload/late skips, write p95 <=150 ms, write/query queue p95 <=75 ms,
filtered/unfiltered query p95 <=50 ms, maintenance p95 <=100 ms, 400 offered
mutations/s with >=350 acknowledged/s, and exact results plus restart state.
A breach is evidence for a layout decision, not grounds to increase limits.

At 250,000 rows, the proposed single-machine gates are: <=64 MiB peak engine
RSS excluding the caller's input corpus and retained results, <=256 MiB cache
occupancy, zero lost acknowledged writes after restart or total cache deletion,
zero overload/late skips at the same offered rate, write p95 <=150 ms, warm
query p95 <=50 ms, cold query p95 <=200 ms, and fresh-process open <=1 s.
Approximate queries require mean recall@10 >=0.90, fifth-percentile recall@10
>=0.80, and <1% short results when exact has ten matches; filtered and
unfiltered classes are measured separately. Exact search remains the oracle.
These are acceptance targets to test, not claims about current performance.

Storage-work ceilings at the offered rate: <=6 PUT/s, <=6 DELETE/s, <=2 MiB/s uploaded
payload including maintenance, <=8 GET and <=1 MiB downloaded per query in the
cold class, <=2 GET and <=256 KiB downloaded per query in the NVMe-warm class,
<=1 LIST/minute in steady serving, and <=1 GiB visible durable object payload
including temporary coexistence. Report retained object count and backup bytes
separately. At a continuous 30-day offered load these ceilings mean at most
15.552 million PUT, 15.552 million DELETE, 43,200 LIST and 5.436 TB uploaded;
the NVMe-warm ceiling means at most 207.36 million GET and 27.179 TB
downloaded. Multiply the measured request/byte counts by the chosen
deployment's published unit prices before a remote cost acceptance. These are
deliberately transparent physical-work limits, not a quoted AWS bill; no MinIO
timer is an AWS price or latency.
The ceilings intentionally rule out a fixed-interval full-base snapshot: even
raw 128,000,000-byte vectors would exceed the two-MiB/s upload allowance if
rewritten more often than about once per minute, before JSON or indexes.

## Measurement and decision sequence

Run one real-data 10,000-row independent-arrival diagnostic on disposable
loopback MinIO with `python3 tools/m19_benchmark.py NEW_OUTPUT --data DATA --independent`.
The runner verifies the M19 data hashes, records source/environment and removes
its MinIO container. This keeps the existing 5,000-row acceptance as baseline.
Attribute snapshot PUT bytes and mutation PUT bytes separately. A full rewrite
at fixed mutation count grows with the base; a changed-data publication should
grow primarily with changed rows plus bounded manifest/index work.

## Result and layout decision

The [final 10,000-row run](m21/independent-10000-final/run.json) used the
pinned local MinIO image on Apple M4/macOS 26.6.2 with Rust 1.98.1. Its
[80 writes and 800 independent queries](m21/independent-10000-final/probe-10000/serve.json)
completed in 19.913 s with no overload or skipped slots. All 800 query results
matched a sequence-specific independent exact oracle; final vectors and
metadata matched after reopen. MinIO cleanup succeeded. A first run exposed a
reporting omission for snapshot classification and recovery I/O; it is retained
as a diagnostic, while the corrected final run is the decision evidence.

| 10,000 × 128 local MinIO | Measured | Declared limit |
|---|---:|---:|
| Write p95 | 111.725 ms | 150 ms |
| Write queue p95 | **99.921 ms** | 75 ms |
| Filtered/unfiltered query p95 | 6.851 / 6.928 ms | 50 ms each |
| Query queue p95 | 5.402 ms | 75 ms |
| Maintenance p95 (4 events) | 95.196 ms | 100 ms |
| Peak whole-process RSS | 44.984 MiB | 64 MiB at this diagnostic |
| Restart open | 119.973 ms, 21 GET, 4,782,996 bytes | <=1 s target |

Serving issued 84 PUT, 69 DELETE, four LIST and zero GET requests. Total PUT
payload was 20,159,131 bytes: 15,041,800 bytes in four complete
`compacted-` snapshots and 5,113,299 bytes in 80 mutation objects. Each
snapshot was about 3.76 MB and its PUT took 45.585–64.869 ms. The snapshot
bytes were 74.6% of uploaded bytes while acknowledging only changed rows.
The query maximum of 110.0 ms shows maintenance can delay an independent read
even though query p95 passed. Existing resident queries generated no remote
GETs; this is not cold/warm cache evidence. The 10,000-row RSS and recovery
measurements do not establish a 250,000-row resource bound.

At fixed update rate, a complete snapshot grows with the base. Multiplying
the measured 10,000-row snapshot size by 25 predicts roughly 94 MB per
250,000-row snapshot, or about 19 MB/s at four snapshots per 20 s. This is an
extrapolation, not a measured SIFT1M size or wire bill. It exceeds the proposed
2 MiB/s upload ceiling by about 9× and would make the 64 MiB RAM target
impossible with the current resident map. Compression alone leaves full-base
rewrite work proportional to row count. M22 must publish changed data and
M23 must avoid opening every vector.

Choose immutable addressable base blocks plus bounded, ID-sorted delta runs
with per-run vector-partition summaries. A versioned root records referenced
blocks, sequence and retry state; an acknowledged mutation remains an immutable
log object until a complete root covers it. A reader pins one root and overlays
newer committed mutations. The block identity and digest are the RAM/NVMe cache
keys; search can select partition blocks and filter postings without loading the
base. A delta run includes deletes and replacement IDs, and a bounded latest-ID
directory prevents stale base candidates from being returned. M22 must prove
the directory and run metadata fit the budget, and bound the log tail and
reclamation backlog before implementation acceptance.

The alternative of rewriting affected partition blocks has poor update locality
for this workload. A 100-row batch distributed across roughly 1,000 base blocks
touches about 95 distinct blocks under uniform placement; at 128 KiB each,
that is about 12 MiB of block writes for roughly 64 KiB of mutation payload.
This estimate is a stated uniform-placement model, not a measured SIFT1M
partition distribution. Immutable deltas preserve changed-data write cost;
periodic consolidation is still necessary and its amplification must be measured.
Splitting a complete snapshot into chunks does not change its full-base work.
No AWS call is needed for this engine-side layout choice.
