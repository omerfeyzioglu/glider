# M19 capacity protocol

Status: first bounded probe completed; acceptance remains open. The 2,000-row
step exceeded queue and maintenance budgets, so no larger step or final soak
was run. A targeted maintenance fix is required before continuing.

Intended deployment: one bounded worker serving a small image-descriptor catalog
from resident vectors backed by the pinned local Docker MinIO. Use SIFT small's
128-dimensional descriptors, squared Euclidean exact k=10, and an application
metadata equality group containing every 100th ID (1%). This tests a real vector
dataset with explicitly synthetic metadata/update traffic; it is not a general
image-retrieval quality or production-user traffic claim. Select the first
2,000, 5,000, then 10,000 base vectors. Stop at the first budget breach, profile
that boundary, and run exactly one final 50-second rehearsal at the largest
passing size. Probe steps last 20 seconds each. If the first step fails or no
boundary is reached, report that result rather than inventing an envelope/limit.

The [SIFT corpus](http://corpus-texmex.irisa.fr/) is obtained from the
[TileDB documented mirror](https://documentation.cloud.tiledb.com/academy/structure/ai-ml/vector-search/quickstart/):
`https://github.com/TileDB-Inc/TileDB-Vector-Search/releases/download/0.0.1/siftsmall.tgz`.
Archive SHA-256: `df5907f88abf25ea8a4ead853266f8405b27f43e64bc306be32dc5531d1e7a93`.
Extract only the two flat archive members, without executing archive content:

- `siftsmall_base.fvecs` (10,000 rows), SHA-256 `1e90414a3254361aba48a0d58e461f7661fb135dabb3da985290e94de8f60fe0`.
- `siftsmall_query.fvecs` (100 rows), SHA-256 `095af38bda2741be721447ba97e9286fa918ece946be92a9ae133276eddc1a10`.

The runner verifies both digests. Data stays outside Git. Invoke
`python3 tools/m19_benchmark.py NEW_OUTPUT --data DATA_DIRECTORY`.
`--smoke` generates a separate deterministic fixture, uses two unpaced rounds,
and verifies correctness only; CI never downloads the dataset or runs a soak.

Four clients each submit one atomic 100-overwrite batch plus ten queries each
second: 400 offered logical mutations/s and 40 queries/s, half filtered.
Each client owns a disjoint quarter of IDs, cycles full 100-ID blocks within
it, and replaces ID `i` at round `r` with base descriptor
`(i + (r+1)*137) % 10000`. Query IDs cycle the 100 supplied query descriptors;
repeated vectors at different boundaries are distinct observations, not distinct
independent queries. Metadata membership stays fixed. Dataset/order/traffic are
deterministic (no random dataset seed). Request IDs encode client and round.
Each query is checked by an independent full-sort oracle replaying the actual
commit order. Every final vector and metadata value is checked after reopen.

Predeclared budgets retain M16's eight commands, 320 KiB encoded admission,
write p95 <=150 ms, each query class p95 <=50 ms, write/query queue p95 <=75 ms,
commit p95 <=100 ms, maintenance-event p95 <=100 ms, >=350 acknowledged logical
mutations/s and peak process RSS <=64 MiB. Recovery in a new process must take
<=1,000 ms, <=64 GETs, <=4 LIST pages and <=16 MiB logical GET payload.
Steady serving per offered second permits <=5 PUTs, <=5 DELETEs (plus two total
for shutdown), <=1 LIST and <=2 MiB HTTP request-body bytes. No query GETs are
expected. These are end-to-end client samples, with arrival lateness separately
reported. Slow clients do not create an unbounded backlog. Rejection is an
explicit failure of the offered workload, never silently retried.

S3 input limits: 128 visible objects, 16 MiB per envelope and 32 MiB aggregate
visible envelope bytes, including ownership and coexisting obsolete snapshots.
Serving caps live rows at the selected size and each encoded document at 4 KiB.
Test over-capacity write rejection before I/O and oversized open before any
snapshot GET. Runtime bounds remain explicit; none are silently increased.

Prepare, serve and final verify execute in separate processes. Cold means a
fresh client process/connection pool, not evicted MinIO/OS caches. Reports retain
source/data hashes, environment, raw latency samples, HTTP counters, logical
GET/PUT payload bytes and per-store-operation time. RSS includes the 10,100 input
descriptors, setup, samples, oracle validation and any same-process warm reopen;
it is a conservative process high-water mark, not isolated engine allocations.
Store operation times include client encoding/validation and network work;
maintenance minus its storage-call time estimates engine-side work, not a CPU
sampling profile. Report the small number of maintenance events explicitly.

At the selected size, one final fresh-process recovery, backup and restore must
verify all state and exact queries. Backup plus restore API time <=2,500 ms,
<=32 logical GETs, <=16 PUTs, <=12 LISTs, <=64 MiB GET payload, <=32 MiB PUT payload
and <=64 MiB process RSS. Timers exclude subsequent oracle checks. Failure tests
lose a successful mutation PUT response, resolve its receipt after isolated
recovery, and reject a partially copied backup while keeping its source usable.
These tests run at the selected size and reuse M15/M16's broader deterministic
publication/cancellation crash matrix. Container removal cleans every namespace.

This envelope chooses loopback MinIO. No larger-envelope remote/AWS behavior is
accepted by these results; M14a remains bounded provider-correctness evidence
only. A remote deployment needs its own stated arrival/latency budgets and
specific provider-dependent validation before inheriting any capacity claim.


## First boundary and attribution

The clean `bbe827d` probe (Apple M4, macOS 26.6.2, Rust 1.98.1,
pinned Docker MinIO) stopped at 2,000 rows. It checked 800 query observations and
all recovered state. [Environment/source](m19/before/run.json),
[raw samples](m19/before/probe-2000/serve.json),
[operation profile](m19/before/probe-2000/profile.json),
[decision](m19/before/decision.json). Container removal succeeded.

Write p95 95.737 ms and filtered/unfiltered query p95 19.034/2.200 ms passed;
401.945 logical mutations/s, 37.688 MiB RSS and 34.570 ms fresh-process open also
passed. Write-queue p95 78.946 ms exceeded 75 ms. Four maintenance events took
68.471, 34.104, 54.061 and 105.897 ms; their p95/max exceeded 100 ms. Four events
are not a stable tail estimate; this is the predeclared stop condition, not a
claim about general production p95. No supported larger envelope exists yet.

The slowest maintenance event spent 47.770 ms in its snapshot PUT, 44.703 ms in
17 serial DELETEs, 3.264 ms in LIST, and about 10.159 ms outside store calls.
This identifies foreground storage work, especially serial cleanup, as the
first actionable stall. The snapshot was already authoritative before cleanup;
obsolete key deletions are independent and never reused. Compare a small bounded
set of simultaneous native DELETEs with continued serial cleanup before adding
background publication, pinned views, a new format or bulk-delete semantics.
This is M19b, a prerequisite fix motivated by the measured first-step failure.
M17/M18's M16 deferral remains valid only for that earlier workload.


## M19b hypothesis

Four native DELETEs in flight at most should reduce the 44.703 ms serial cleanup
component enough to fit the same queue/maintenance budgets. Keep snapshot
publication and cleanup synchronous with the owner; do not change batch size,
thresholds, workload or acceptance budgets. This adds no retries, new persisted
format, writer, background backlog or S3 bulk-delete API. All deletions target
the already validated obsolete set; any partial failure poisons the handle and
recovery recomputes counts. SDK default parallel delete streaming uses 20 calls;
the chosen group of four is an explicit small bound, not a parameter sweep.

Compare against the retained first probe, then continue the original row steps
only if it passes. The after-run operation profile reports one `remove_many`
wall interval instead of summing overlapping per-key DELETE durations. HTTP
attempt/byte counts and end-to-end timing definitions remain comparable.
