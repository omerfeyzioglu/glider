# M20 snapshot encoding at the measured SIFT boundary

Status: accepted after the separate M20a result-allocation fix.
[PR #48 CI](https://github.com/omerfeyzioglu/glider/actions/runs/36327978017) passed,
including the 5,000-row recovery smoke. The selected envelope is 5,000×128 SIFT descriptors on
local MinIO, with unchanged latency, throughput, RSS and recovery budgets.

M19/M19b established 2,000×128 SIFT serving and stopped at 5,000 rows because
write-queue p95 was 95.972 ms against 75 ms. The slowest maintenance operation
spent 58.833 ms in snapshot PUT, 26.546 ms outside store calls and only 5.060 ms
in cleanup. Exact queries met their budgets, so ANN is not justified. The
[retained 5,000-row baseline](m19/cleanup/probe-5000/serve.json) and
[profile](m19/cleanup/probe-5000/profile.json) are sufficient; do not rerun them.

Hypothesis: SIFT's integral f32 values currently serialize with a redundant
`.0` suffix. The existing JSON schema/reader accepts integer number tokens with
identical f32 values. Emitting exactly represented integers in [-2^24, 2^24]
should reduce each 5,000×128 snapshot by exactly 1,280,000 bytes and reduce
formatting and PUT work enough to meet the existing queue limit. Preserve
negative zero and normal serialization outside that exact integer fast path.
Only single-object snapshots use it; retry payload identity, mutation logs,
chunk byte-reuse and IVF identity serialization stay unchanged. Version 4
continues to describe the same schema and remains readable by the prior reader.

Alternatives: eliminating snapshot clones saves temporary RAM but leaves the
measured PUT volume; a binary/compressed format requires compatibility and
bounded decoding work; background maintenance adds publication coordination
and retention. The existing number representation offers the smallest change
addressing both encoding work and bytes for this intended workload. No claim
is made that arbitrary fractional embeddings have the same improvement.

Use `python3 tools/m19_benchmark.py NEW_OUTPUT --data DATA --m20` after tests.
Run only the failed 5,000-row step for 20 seconds, with exactly the M19 budgets,
input, four-client arrival pattern and measurement definitions. If it passes,
run one final 50-second workload and separate-process backup/restore/failure
rehearsal at 5,000 rows. Stop on failure; do not sweep or proceed to 10,000.
All numeric gates in [M19](M19.md) remain unchanged. CI uses a synthetic two-round
5,000-row correctness smoke, never a timed performance acceptance run.

Tests must preserve f32 bits at positive/negative zero, fractional values,
integer boundaries, extrema/subnormals and reproducible random finite patterns;
verify the prior f32 decoder, checkpoints, compaction, request receipts and
unchanged canonical retry payload. Run existing publication/recovery/corruption
and MinIO failure tests before claiming acceptance. No AWS test is needed for
this JSON representation decision; remote capacity acceptance stays open.


## Memory gate investigation

The clean `de5d1ad` [integer-only probe](m20/integers/probe-5000/serve.json)
reduced HTTP request-body bytes from 17,862,121 to 12,742,121 (exactly 5,120,000,
four snapshots ×1,280,000). Write-queue p95 fell to 69.679 ms and maintenance
p95/max to 64.567 ms, passing latency gates. RSS 70.828 MiB exceeded 64 MiB,
so no final soak ran. This is not acceptance.

A 20-round unpaced real-data attribution run isolates stages without another
long soak. [Profile](m20/memory-diagnostic/probe-5000/profile.json) shows high-water
RSS 16.453 MiB after loading inputs, 26.797 after cold open, 70.203 after serving,
70.422 after oracle checks and 73.891 after warm reopen. An experiment borrowing
snapshot documents instead of cloning them reduced serving RSS to 66.375 MiB
([profile](m20/borrow-diagnostic/probe-5000/profile.json)), still over budget.
That alternative does not address the main retained allocation and is not selected.
Unpaced diagnostic timings are not compared with paced latency acceptance.

Inspection identified the retained allocation: exact search truncates its scored
candidate Vec to k but returns its original capacity. The benchmark intentionally
retains query results for later independent oracle checks, so each ten-neighbor
result can retain storage proportional to the full scanned set. Fix the public
result allocation separately (M20a), keeping temporary scoring and exact ordering
unchanged. Then rerun only the 5,000-row target with the numeric snapshot change
and original RSS/latency gates. Completed results remain caller-owned; this fix
does not make an arbitrary number of retained results free.


## Final result

The clean `9601d0b` [targeted after-run](m20/final/probe-5000/serve.json)
passes all predeclared 5,000-row gates. [Environment/source](m20/final/run.json),
[profile](m20/final/probe-5000/profile.json), [decision](m20/final/decision.json).
It reuses the retained M19b baseline; no 10,000-row run or broad sweep was made.

| 5,000-row, 20-second probe | M19b baseline | Final change | Limit |
|---|---:|---:|---:|
| Write p95 ms | 105.921 | 81.183 | 150 |
| Write queue p95 ms | 95.972 | 70.433 | 75 |
| Filtered query p95 ms | 20.551 | 19.710 | 50 |
| Unfiltered query p95 ms | 4.441 | 4.204 | 50 |
| Maintenance-event p95/max ms | 92.415 | 62.623 | 100 |
| Acknowledged logical mutations/s | 401.848 | 401.888 | >=350 |
| Peak process RSS MiB | 61.422 | 35.031 | 64 |
| Fresh-process open ms | 61.270 | 52.315 | 1,000 |
| HTTP request-body bytes | 17,862,121 | 12,742,121 | <=41,943,040 |

Both probes checked 800 query observations and recovered state, with identical
84 PUT, 69 DELETE, four LIST and zero query GET counts. The exact byte reduction
is the predicted four ×1,280,000. The separate M20a allocation regression proved
capacity 8,192 for a single returned neighbor before the fix; results now retain
exactly their returned neighbor capacity for both metrics and filter/k boundaries.
The f32-bit tests preserve negative zero, extrema/subnormals, exact integers and
seed-42 finite bit patterns through both snapshots and recovery, with unchanged
retry identity/receipts. The snapshot-borrowing alternative was not retained;
its diagnostic source is recorded in commit `82612d2`, while `3bcb122` restores
the selected owning snapshot serialization with diagnostic instrumentation.

The one final [50-second workload](m20/final/final-5000/serve.json) at 5,000 rows
checked 2,000 query observations and all final vectors/metadata. Write/queue p95
were 76.001/66.390 ms; filtered/unfiltered query p95 18.248/4.289 ms;
maintenance p95 66.337 ms (12 events); throughput 400.751 logical mutations/s;
RSS 35.469 MiB; fresh-process open 54.066 ms. It used 212 PUT, 205 DELETE,
12 LIST, zero GET and 35,458,484 request-body bytes with no HTTP/transport errors.
The fixed workload and few maintenance events do not establish general tails.

[Separate-process verification](m20/final/final-5000/verify.json) passed all
state/oracle, partial-backup, successful-PUT-response-loss, retained-receipt,
isolated takeover and oversized-open checks. Fresh recovery took 60.857 ms,
backup 92.801 ms and restore 109.872 ms; backup/restore used 12 logical GETs,
seven PUTs, nine LISTs, 9,451,808 GET payload bytes and 5,671,076 PUT payload bytes.
Verification process RSS was 39.438 MiB. Every numeric gate passed and the entire
MinIO container was removed. Full all-feature tests, Clippy and the MinIO
failure/restart matrix passed locally and in the successful PR CI.

This expands the tested row count from 2,000 to 5,000 for the selected descriptor
workload while preserving exact search and one committer. Larger sizes, fractional
embedding workloads and remote/AWS latency are unvalidated. ANN, multiple
committers and background publication remain deferred; the measured bottlenecks
were snapshot representation and retained result allocations.
